## Remediation scope

### Request-body and native-input security

- Booking checkout now streams URL-encoded form input through a 4 KiB byte cap.
- Stripe webhook verification receives the exact raw `Buffer` after a 1 MiB
  streamed cap; declared and undeclared lengths both fail closed when oversized.
- Native device registration is capped at 12 KiB, binds the actor to the
  authenticated account, and treats tokens/installation IDs as opaque values.
- Malformed metadata and streams, SQL-like profile strings, oversized bodies,
  opaque-ID whitespace/control/suffix/size cases, account substitution, and
  normalization attacks have deterministic negative tests.

### Public-profile boundary

- `20260804052000_secure_public_profiles_projection.sql` introduces a dedicated
  `profile_projection` schema, a read-only allowlisted projection table, RLS, an
  empty-`search_path` synchronization function, and a `security_invoker` public
  view. Client roles receive `USAGE` without `CREATE` and cannot execute the
  synchronization function.
- Five signed-out consumers now select relationship IDs and hydrate public
  display fields through `public_profiles`; authenticated owner/moderator paths
  remain explicit so the existing grant is not revoked underneath them.
- Sponsored campaigns are filtered through the public projection before
  ranking, preventing private/suspended/banned/internal advertisers from
  rendering generic clickable ads. A behavioral regression proves a hidden
  highest-scoring campaign cannot suppress a lower eligible public campaign.
- Large profile-ID sets are de-duplicated, split into 100-ID batches, and fetched
  sequentially so pagination cannot launch unbounded concurrent database calls;
  a 205-ID behavioral fixture measures maximum active batch concurrency at one.
- This migration and application refactor do **not** cure the existing
  authenticated full-column base-table access. A separately reviewed consumer
  inventory, narrow owner/moderator interfaces, privilege removal, and direct
  malicious signed-in query tests are required.

### Association routing

- HTTPS association requests for apex and `www` bypass only the host
  canonicalization redirect and return direct JSON.
- HTTP production-host requests still redirect to canonical HTTPS, and ordinary
  HTTPS `www` pages still redirect to apex.
- The local production-server matrix passed four HTTPS host/path responses, two
  HTTP canonical redirects, and one ordinary `www` redirect using synthetic
  identifiers. Production remains unchanged.

### Stripe architecture and evidence

- Current develop uses Accounts v1 Express onboarding, a platform booking
  Checkout with a separately client-paid 2% line item, official-TTC platform
  Merch, gated destination charges for non-official Merch, platform web ads, and
  one webhook secret without connected-account scope.
- Main-only direct-charge, integration-identifier, native-ad-credit, and
  independent release-gate changes were not imported.
- If the owner confirms that the provider is the merchant/customer owner and
  bears fee/loss responsibility, the documented conditional target is Accounts
  v2 Merchant with full dashboard, Stripe fee/loss collection, card payments,
  v2 hosted links, and direct charges with a 2% application fee. The Express
  application/platform alternative remains valid if TTC is the platform owner.
- Develop lacks independent booking-checkout and onboarding release gates; they
  must be added before any live binding can make those flows reachable.
- Two same-URL webhook destinations are reported: one `2026-06-24.dahlia`
  destination with 12 events and one default-version destination with 14 events.
  Endpoint IDs, account/connected-account sources, secret mappings, and account
  default API version are unverified.
