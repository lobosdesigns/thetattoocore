# v1.1.0 Stripe Architecture Decision

**Status:** Conditional recommendation; implementation and owner approval required

**Decision date:** 2026-08-04
**Production effect:** None. This document does not authorize account creation,
onboarding, webhook changes, live checkout, refunds, transfers, payouts, or any
other production action.

## Decision

Current develop is not the intended long-term booking-payment architecture. It
uses platform-owned booking charges and a legacy Accounts v1 Express flow for
seller payout setup.

The safest supported target for **new booking-provider accounts** is
conditionally:

- Accounts v2 with the Merchant configuration;
- <code>dashboard: "full"</code>;
- <code>defaults.responsibilities.fees_collector: "stripe"</code>;
- <code>defaults.responsibilities.losses_collector: "stripe"</code>;
- the Merchant <code>card_payments</code> capability requested;
- direct Checkout charges created in the provider account context; and
- TTC's 2% revenue retained as an application fee.

Stripe describes this as the Stripe-owned-pricing SaaS model: the connected
business is merchant of record, pays Stripe fees, carries its payment activity
in its own balance, and uses direct charges. The full Dashboard gives that
business Stripe-hosted access to payments, refunds, disputes, reports, and
payouts. See Stripe's current
[SaaS platform model](https://docs.stripe.com/connect/saas),
[Accounts v2 configuration rules](https://docs.stripe.com/connect/accounts-v2/connected-account-configuration),
and [direct-payment task](https://docs.stripe.com/connect/saas/tasks/accept-payment).

This recommendation is **conditional on an owner/legal decision that each
artist or studio, rather than TTC, is the merchant of record for its booking
deposit and owns the customer relationship**. Code cannot make that decision.
If TTC is the merchant of record, controls fulfillment as a marketplace, or
must bear provider losses, this target is wrong; the owner must approve a
marketplace configuration and the charge flow must be redesigned before
onboarding.

The target applies only to booking deposits. Web ad purchases remain
platform-owned. Current develop's official Merch charges and non-official
destination-charge flow are separate business models and must not be silently
converted by a booking-account migration.

### Current webhook event contract

The develop handler has explicit behavior for:

- <code>checkout.session.completed</code>
- <code>checkout.session.async_payment_succeeded</code>
- <code>checkout.session.async_payment_failed</code>
- <code>checkout.session.expired</code>
- <code>charge.refunded</code>
- <code>refund.failed</code>
- <code>charge.dispute.created</code>
- <code>charge.dispute.updated</code>
- <code>charge.dispute.closed</code>
- <code>charge.dispute.funds_withdrawn</code>
- <code>charge.dispute.funds_reinstated</code>
- <code>account.updated</code>

It does not handle Application Fee events and does not distinguish a platform
event from an event on a connected account. Stripe distinguishes account
webhooks from Connect webhooks: connected-account activity is sent from a
destination configured for connected-account events and carries a top-level
account value. See [Connect webhooks](https://docs.stripe.com/connect/webhooks).

Because each Stripe event destination has its own signing secret and current
develop reads only one environment variable, the two observed same-URL
destinations cannot both be considered intentionally mapped. Which one, if
either, matches <code>STRIPE_WEBHOOK_SECRET</code> is **UNVERIFIED**.

### Current database assumptions

The develop schema assumes:

- <code>public.stripe_connect_accounts</code> has one row per profile, one
  <code>acct_</code> identifier, a legacy account type constrained to
  Express/Standard/Custom, a <code>livemode</code> marker, v1 readiness
  booleans, a disabled reason, and a JSON array of currently-due requirements.
- The profile ID primary key permits only one stored connected account per
  profile. The schema does not model separate purposes such as Merch
  destination account versus booking Merchant account.
- <code>booking_requests</code> stores deposit, platform fee, total, Checkout
  Session ID, and PaymentIntent ID. Its money constraint requires
  <code>total_cents = deposit_amount_cents + platform_fee_cents</code>. It has no
  connected Account ID, Application Fee ID, fee-payer field, or charge-model
  field.
- <code>merch_orders</code>, <code>ad_campaigns</code>, and booking rows store
  platform Checkout/PaymentIntent identities used by the one webhook handler.
- <code>stripe_webhook_events</code> deduplicates on <code>event_id</code>; it
  has no account/destination scope.
- Connect readiness and payment identifiers are intended to be server/service
  data, but develop still exposes full Connect rows to authenticated
  owners/moderators and all booking columns (including Stripe identities) to
  booking participants/moderators. The later main-only booking column-privilege
  hardening is not present and must be reconciled before connected booking.

Those fields do not represent Accounts v2 Merchant configuration, Dashboard
access, fee/loss responsibility, or capability status.

| Question | Current booking platform charge | Current non-official Merch destination charge | Conditional Accounts v2 booking target |
| --- | --- | --- | --- |

| Merchant of record in Stripe flow | TTC/platform | TTC/platform by default | Provider |
| Stripe processing fees | TTC/platform | TTC/platform | Provider, through <code>fees_collector = stripe</code> |
| Negative balance liability | TTC/platform | TTC/platform | Stripe is liable if the provider cannot repay its connected-account negative balance; TTC remains liable for TTC's own platform balance |

Stripe's current
[controller-property mapping](https://docs.stripe.com/connect/migrate-to-controller-properties)
shows that <code>type: "express"</code> maps to platform loss responsibility,
Stripe requirement collection, Express Dashboard, and
<code>application_express</code> fee behavior. For indirect charges, Stripe
still collects fees from and debits refunds/disputes against the platform. The
[Accounts v2 configuration guide](https://docs.stripe.com/connect/accounts-v2/connected-account-configuration)
defines the proposed full/Stripe/Stripe combination.

## Are direct booking charges appropriate?

**Conditionally yes; not yet an owner-approved fact.**

Direct charges align technically when the artist/studio runs an independent
business, owns the client relationship, is merchant of record for the
appointment deposit, pays its processing fees, funds refunds, and handles
disputes. Stripe identifies direct charges as the SaaS pattern and requires an
active Merchant card-payments capability. The provider's full Dashboard then
exposes the payment operations that correspond to those responsibilities.

Direct charges are not appropriate if TTC is the merchant, sells one combined
service across multiple providers, must control fund release as a marketplace,
or contractually carries provider losses. In that case, keep an indirect
marketplace model and select an Express/application/application configuration
only after business, legal, tax, refund, and dispute review.

## Required Accounts v2 implementation

### Account ownership and purpose

Current <code>stripe_connect_accounts</code> conflates one profile with one
legacy account used for seller destination charges. The target must model
purpose explicitly:

- <code>merch_destination_legacy</code> for any retained v1 Express account;
- <code>booking_merchant</code> for the new v2 Merchant account; and
- environment/mode as part of identity.

Do not silently reuse an Express Merch account for full-Dashboard booking. The
Dashboard and responsibility values are creation-time decisions. Stripe says
Dashboard choice is immutable and Merchant responsibility values cannot be
updated later. A mismatched account must be retired for new use and replaced
through an owner-approved provider communication/reconciliation plan.

### Account creation and onboarding

1. Split booking-provider onboarding from the current generic seller payout
   route.
2. Replace new booking-account creation through
   <code>POST /v1/accounts</code> with
   <code>POST /v2/core/accounts</code> and explicitly request:
   - <code>dashboard = "full"</code>
   - <code>configuration.merchant.capabilities.card_payments.requested = true</code>
   - <code>defaults.responsibilities.fees_collector = "stripe"</code>
   - <code>defaults.responsibilities.losses_collector = "stripe"</code>
   - Merchant configuration, requirements, defaults, and identity in the
     response <code>include</code> set.
3. Do not add Recipient configuration or request
   <code>stripe_balance.stripe_transfers</code> for direct charges. Stripe
   identifies Recipient/transfer capability as the indirect-charge
   configuration, while Merchant includes card payments and payouts. See
   [Accounts v2](https://docs.stripe.com/connect/accounts-v2).
4. Do not add Customer configuration unless TTC later approves a separate
   provider-subscription use case.
5. Create a v2 Account Link through
   <code>POST /v2/core/account_links</code> for Merchant onboarding. Use
   Stripe-hosted onboarding in an external browser, never an embedded mobile
   WebView. Stripe states that Account Links are single-use and that returning
   from onboarding does not prove completion. See
   [Accounts v2 onboarding](https://docs.stripe.com/connect/saas/tasks/onboard).
6. On return, retrieve the v2 Account with required included properties and
   verify profile binding, account ID, environment, Dashboard, responsibility
   values, Merchant configuration, requirements, and exact capability statuses.
7. Readiness must require active Merchant <code>card_payments</code> and
   Merchant <code>stripe_balance.payouts</code> capabilities plus no blocking
   current requirements; it must not rely only on v1
   <code>charges_enabled</code>/<code>payouts_enabled</code>.
8. Use a Stripe Sandbox for the API-version/SDK combination. Stripe's current
   Accounts v2 examples use a preview version. Do not silently replace the
   current v1 payment/webhook version with that preview.

### Direct Checkout, refunds, and disputes

The recovered main-line connected Checkout design is the starting point, not
proof of Accounts v2 compatibility:

1. Continue using v1 Checkout/PaymentIntent/Charge/Refund/Application Fee
   endpoints in the v2 Account context. Stripe explicitly supports v2 Account
   IDs in v1 endpoints.
2. Create the Checkout Session with the connected Account header and
   <code>application_fee_amount</code>; do not use destination
   <code>transfer_data</code>.
3. Persist exact account, Checkout Session, PaymentIntent, Charge, and
   Application Fee identities with amount/currency/owner metadata.
4. Explicitly refund TTC's Application Fee according to approved full/partial
   refund policy. Stripe warns that an application fee is not automatically
   refunded. See [direct-charge refunds](https://docs.stripe.com/connect/direct-charges).
5. Retrieve/refund direct-charge objects in the same connected context.
6. Let the provider use its full Dashboard for refunds/disputes, while TTC
   preserves signed-event reconciliation, operational holds, idempotent admin
   support, and audit trails.
7. Add tests for provider-initiated and TTC-assisted refunds, partial refunds,
   insufficient connected balance, failed/pending refunds, dispute lifecycle,
   Application Fee reconciliation, retries, and out-of-order events.

### Additive database migration

Use a new forward-only migration. Do not edit any 202607 or 20260803 file.
The safest additive shape is:

1. Preserve <code>stripe_connect_accounts</code> as the legacy v1 identity and
   readiness store.
2. Add a service-only account-binding/configuration table keyed by Stripe
   Account ID with profile ID, purpose, environment, API family, Dashboard,
   fee collector, loss collector, requirements collector, Merchant
   card-payments status, Merchant payouts status, requirement snapshot, status
   timestamps, and retirement state. Enforce one active account per
   <code>(profile_id, purpose, environment)</code>.
3. Import existing rows only as legacy v1 records with an explicit legacy
   purpose. Do not infer full/Stripe/Stripe values from <code>acct_</code> shape
   or <code>account_type</code>.
4. Add a service-only resolver/RPC that returns a booking-ready account only
   when the exact target configuration, environment, ownership, and capability
   requirements pass.
5. Add the connected-direct booking routing and privilege protections from the
   main-only migrations only after reconciling whether those exact files are
   already applied elsewhere.
6. Keep every historical booking/Merch order bound to its original charge
   model and Account/PaymentIntent identifiers. Never rewrite a platform or v1
   charge to a v2 account.
7. Extend webhook storage so source, destination generation, API family,
   account context, and event ID participate in dedupe without weakening
   historical platform claims.
8. Revoke all client roles from account configuration and payment-routing data;
   expose only a non-sensitive readiness result through an allowlisted view if
   the UI needs it.
9. Document forward repair: gate onboarding and checkout creation off, keep
   webhooks active, reconcile configuration rows additively, and resume only
   after event/payment reconciliation. Never drop payment history as rollback.

### Backward compatibility

- Current v1 Express accounts remain v1 and continue through a legacy status
  path. Do not relabel them as Accounts v2.
- Current platform bookings remain platform bookings for their entire
  lifecycle and use the current refund/webhook path.
- Existing destination-charge Merch orders remain platform charges and retain
  transfer reversal/refund behavior.
- New booking accounts use v2 only after owner approval and Sandbox proof.
- The account resolver branches on stored purpose, API family, environment,
  and configuration, not merely Account ID shape.
- Existing v1 snapshots and new v2 thin account events use separate parsers and
  destination scopes.
- Stripe supports incremental coexistence but discourages indefinite dual
  Accounts versions. See
  [Accounts v2 migration guidance](https://docs.stripe.com/connect/accounts-v2/migrate-integration).

## Restricted-key plan

Current develop uses one server-side <code>STRIPE_SECRET_KEY</code> for account
creation, Account Links, Checkout, retrieval, expiration, and refunds. Its key
kind, access policy, and effective permissions are **UNVERIFIED**.

Before changing keys, use Sandbox request logs to inventory every call. Stripe
recommends a restricted key per service/use case, with GET mapped to Read and
POST/DELETE mapped to Write, then testing every path for denied requests before
creating an equivalent live key. See
[restricted API keys](https://docs.stripe.com/keys/restricted-api-keys) and
[key-management practices](https://docs.stripe.com/keys-best-practices).

Proposed least-privilege split:

| Service key | Permissions to prove in Sandbox | Exclude unless request logs prove a need |
| --- | --- | --- |
| v2 booking provisioning | Accounts v2 Write; Account Links v2 Write; connected-account access for those resources | Transfers, payouts, balances, external accounts, tokens, files, Customers, Products, Prices |
| Connected booking Checkout | Checkout Sessions Write in connected contexts; PaymentIntents Read; Charges Read; Application Fees Read | Accounts Write, Transfers Write, Payouts Write |
| Connected booking refund operator | Refunds Write in connected contexts; Charges Read; PaymentIntents Read; Application Fees Read | Checkout/account creation, Transfers/Payouts Write |
| Webhook reconciliation | Accounts v2 Read; Charges Read in connected contexts; PaymentIntents Read only if actual handler retrieval requires it | Payment, refund, transfer, payout, or account writes |
| Platform Checkout/refund | Platform Checkout Sessions Write; Charges/PaymentIntents Read; Refunds Write only for the flows proved by platform tests | Connected-account provisioning and transfer/payout writes |

If the Worker cannot inject separate keys per module, refactor key selection and
tests first. Do not grant every service's permissions to one broad key merely
to avoid that work. Store keys only in the runtime secret store, never log them,
apply access policies where the infrastructure has a stable network identity,
and use delayed expiry only for a controlled rollback window.

### Target destination partition

Do not collapse platform and connected-account traffic into one ambiguous
secret scope. Converge on explicit, non-overlapping destinations:

1. **Platform v1 destination:** platform events only, a platform-specific URL
   such as <code>?source=platform-v1</code>, and one platform signing secret.
   Required by current develop: the four Checkout Session lifecycle events,
   <code>charge.refunded</code>, <code>refund.failed</code>, and the five listed
   dispute events. If connected-direct booking is added, also subscribe this
   platform destination to <code>application_fee.created</code> and
   <code>application_fee.refunded</code> after their handlers/tests exist.
2. **Connected-payments v1 destination:** events on connected accounts only, a
   source-specific URL such as <code>?source=connect-v1</code>, and one Connect
   signing secret. Retain <code>account.updated</code> for legacy v1 readiness.
   If legacy/main-line connected direct payments must coexist, add the four
   Checkout lifecycle events, refund failure/refunded events, and five dispute
   events only after account-scoped handlers/tests are present.
3. **Accounts v2 thin-event destination:** a separate source-specific URL and
   signature/parser path for
   <code>v2.core.account[requirements].updated</code>,
   <code>v2.core.account[configuration.merchant].capability_status_updated</code>,
   <code>v2.core.account[configuration.merchant].updated</code>, and
   <code>v2.core.account.updated</code>. Add
   <code>v2.core.account[future_requirements].updated</code> only if approved
   onboarding stores future requirements. Configure these Account v2 events
   from <code>Your account</code> (<code>events_from: ["@self"]</code>), because
   the v2 Account objects live in the platform account. Keep v1
   <code>account.updated</code> and connected direct-charge events in a
   connected-account destination (<code>events_from: ["@accounts"]</code>).

Stripe recommends a new thin destination for Accounts v2 events. The handler
must retrieve the versioned event or current resource using the event context,
not parse it as a v1 snapshot. See the
[Accounts v2 event migration instructions](https://docs.stripe.com/connect/accounts-v2/migrate-integration)
and [Event Destinations v2 API](https://docs.stripe.com/api/v2/core/event-destinations/create).
Do not subscribe to any event before a deterministic handler/test exists.

### Exact safe consolidation procedure

This is an owner-authorized future operation, not work performed by this
certification:

1. Keep both existing destinations enabled. In a private evidence record,
   capture each endpoint ID, source scope, complete event set, effective API
   version, creation/update time, enabled status, URL, and a non-secret label
   for its signing secret. Capture the runtime environment and Worker version
   holding each secret without displaying secret values.
2. Stop if either endpoint ID, source scope, event list, version, or secret
   mapping cannot be proven. Do not rotate, disable, or delete anything.
3. Implement repository routes that require an explicit source query/path and
   verify exactly one expected secret for that source. Platform events with an
   unexpected connected-account context and connected events without a valid
   account must fail closed.
4. Preserve the current handler for historical platform events while adding
   separate v1 Connect and v2 thin parsers. Include source/account context in
   idempotency claims.
5. In a Stripe Sandbox, create disabled replacement destinations with distinct
   source values and exact event partitions. Deliberately pin and test
   <code>snapshot_api_version</code> for the v1 snapshot destinations. Accounts
   v2 thin notifications are unversioned; deliberately pin and test the
   API/SDK version used to retrieve their full event or resource instead.
   Stripe's safe versioning procedure recommends a distinguishing query
   parameter and a disabled new endpoint before cutover. See
   [webhook versioning](https://docs.stripe.com/webhooks/versioning).
6. Enable one Sandbox replacement at a time. Send source-appropriate non-money
   events; prove signature verification, source/account scope, dedupe, resource
   retrieval context, and expected 2xx. Prove the wrong secret/source returns
   4xx.
7. Run payment, webhook, malicious-input, refund, dispute, account-status, and
   retry/out-of-order suites.
8. Only after separate production authorization, create production
   replacements disabled, verify their metadata, place each signing secret in
   its exact runtime variable, and deploy source-specific handlers with
   onboarding/payment creation gates still off.
9. Enable replacements one at a time. Prove no unhandled events, wrong-source
   events, duplicate side effects, retry backlog, or version errors in Stripe
   delivery logs and sanitized application audit records. Keep old
   destinations available during the rollback window.
10. Disable, but do not immediately delete, only a proven redundant old
    destination. Reconcile outstanding retries first; Stripe notes that
    disabling ends redelivery of intentionally failing events.
11. After the owner-approved observation window and a zero-backlog review,
    remove the redundant destination, rotate/expire its unused signing secret,
    re-verify surviving IDs/scopes/versions, and update private evidence. Never
    commit secret values.

## Owner and business decisions still required

Each item must be decided in writing before account creation:

- Is the provider or TTC merchant of record for a booking deposit?
- Does the owner accept the Stripe-owned pricing model: provider-paid Stripe
  processing fees and Stripe loss responsibility?
- Does each artist own an Account, does a studio own one for its artists, or
  can both exist? What happens when an artist changes studios?
- Does the provider issue refunds and respond to disputes in the full
  Dashboard? What reviewed TTC support/admin path and SLA remain?
- Is TTC's 2% application fee correct, disclosed, taxable, and refundable in
  full or proportionally for each cancellation/refund case?
- Under the target, should the provider absorb the 2% from the deposit, or
  should the client pay a separately disclosed fee? The recovered main-line
  design assumes provider-paid; current develop assumes client-paid.
- Who owns tax, receipt, statement-descriptor, customer-support, no-show,
  cancellation, and regulatory duties for booking deposits?
- Which countries, currencies, entity types, payment methods, minimum deposits,
  and provider eligibility rules are allowed?
- Is onboarding up-front or incremental, and which future requirements are
  collected?
- May existing legacy Express accounts remain for Merch, or must any be retired?
  Can one profile legitimately own separate Merch and booking accounts?
- Does the owner approve the Accounts v2 preview version required by the
  selected Stripe documentation/SDK combination after Sandbox validation?
- Who may create restricted keys, map webhook secrets, rotate credentials, and
  perform future destination consolidation?
- Do Terms, Privacy, booking policies, support procedures, and provider
  communications match provider merchant-of-record status and full Dashboard
  access?

**No-go now.** Do not deploy or enable Connect onboarding, booking Checkout, or
new destination-charge creation. Current develop lacks independent onboarding
and booking-Checkout feature gates, so implement and test fail-closed gates
before any production-capable release; do not describe those two paths as
already gate-off.

2. current develop and main-only payment histories are reconciled without
   editing an applied migration;

   pass review;
