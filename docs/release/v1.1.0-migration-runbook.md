## Security Checks

- RLS remains enabled where new tables are introduced.
- Grants/revokes restrict privileged functions to intended roles.
- Security-definer functions declare explicit `search_path`.
- Caller identity is derived through trusted auth context or server-authorized checks, not caller-controlled user IDs alone.
- No migration truncates tables or intentionally deletes production data.
- Policy and constraint drops are replacements, not access removal without corresponding recreated policy/constraint.

## Preflight Checks

Run immediately before production migration application:

```sql
select current_database();
select now();
select count(*) from public.notifications;
select count(*) from public.booking_requests;

with duplicate_message_notifications as (
  select
    message_id,
    recipient_id,
    type,
    count(*) as duplicate_count
  from public.notifications
  where message_id is not null
  group by message_id, recipient_id, type
  having count(*) > 1
)
select
  count(*) as duplicate_group_count,
  coalesce(sum(duplicate_count - 1), 0) as excess_duplicate_row_count
from duplicate_message_notifications;

select a.id as first_booking, b.id as overlapping_booking
from public.booking_requests a
join public.booking_requests b
  on a.id < b.id
 and a.recipient_id = b.recipient_id
 and a.scheduled_start_at is not null
 and a.scheduled_end_at is not null
 and b.scheduled_start_at is not null
 and b.scheduled_end_at is not null
 and a.status in ('accepted', 'rescheduled', 'deposit_pending', 'deposit_paid')
 and b.status in ('accepted', 'rescheduled', 'deposit_pending', 'deposit_paid')
 and tstzrange(a.scheduled_start_at, a.scheduled_end_at, '[)') &&
     tstzrange(b.scheduled_start_at, b.scheduled_end_at, '[)')
limit 20;
```

Expected duplicate-message-notification result:

```text
duplicate_group_count | excess_duplicate_row_count
0                     | 0
```

The duplicate-message-notification query mirrors the `notifications_message_recipient_type_unique` partial unique index from `20260726200000_dedupe_message_notifications.sql`: `public.notifications (message_id, recipient_id, type) where message_id is not null`. PostgreSQL unique indexes treat rows outside the partial-index predicate as not indexed, so rows with `message_id is null` are intentionally excluded. The existing `notifications_message_id_type_check` constraint requires every non-null `message_id` notification to use `type = 'message'`; the grouped `type` column remains part of the preflight because it is part of the unique index.

If `duplicate_group_count` is nonzero, stop safely. Do not manually delete or edit production notification rows during the release mission unless a separately reviewed corrective migration is certified. Zero duplicate groups permits proceeding to the next preflight gate.

Optional diagnostic query, if the aggregate is nonzero:

```sql
select
  message_id,
  recipient_id,
  type,
  count(*) as duplicate_count
from public.notifications
where message_id is not null
group by message_id, recipient_id, type
having count(*) > 1
order by duplicate_count desc, message_id, recipient_id, type
limit 20;
```

This diagnostic query is SELECT-only and returns identifiers and counts only. It must not be expanded with message bodies, notification body text, profile fields, email addresses, tokens, or other private content.

Stop if either duplicate message-notification rows or overlapping active scheduled bookings appear and the corresponding migration cannot be applied safely.

## Backup Confirmation

Before applying any migration:

1. Confirm the latest Supabase backup or point-in-time recovery window is healthy.
2. Record the current production application commit and Worker version.
3. Confirm no active checkout, admin bulk operation, or booking migration-sensitive workflow is in progress.
4. Keep a rollback owner online for the entire migration and smoke window.

## Stop Conditions

- Preflight duplicate or overlap query returns rows that are not already remediated.
- Any migration fails or runs longer than the approved change window.
- RLS, grant, or function verification does not match expected state.
- Application deploy is not ready to follow migration application.
- Backup/PITR status cannot be confirmed.

## Rollback Procedure

Prefer Worker rollback first if the application release is unhealthy after migrations. If a migration itself causes a production incident:

1. Stop new deployment actions.
2. Put payment and admin mutation gates in their safest available mode.
3. Restore the prior Worker version if app behavior is the issue.
4. For unapplied or immediately failed migrations, use the rollback notes in each migration where present.
5. For migrations that have accepted production writes, use Supabase PITR or a forward corrective migration instead of ad hoc destructive SQL.
